how it works

Selection vectors, not copied rows.

Filters return 32-bit physical row IDs. The next operator walks only those rows, input order is preserved, and every incoming ID is bounds-checked: a corrupt selection is an error, not an out-of-bounds read.

Validity bitmaps

Nullness lives beside the values, one bit per row packed into 64-bit words, so value arrays stay dense and typed. A comparison with NULL is unknown, and unknown is never selected. Inner joins never match null keys, not even null against null.

Why the vector path can lose

Each batch writes a byte mask, then rereads it to compact. That gives the compiler a straight numeric loop to vectorize, and it's also a cost a scalar loop never pays. At small inputs or very selective scans, the mask costs more than it saves. Both sides are reported.

TPC-H Q1, fused

The vector executor builds one validity/predicate mask per batch, then updates all six aggregate states in a single pass, without materializing an intermediate table.

where it stops holding

Vectorization is a trade, and the table shows both sides.

  • Small inputs loseAt 1,000 rows the vector path runs at 0.87× and at 10,000 rows with 7% survival at 0.93×. The mask and compaction pass cost more than they save.
  • Selective scans cross over lateAt a million rows with 7.4% survival the gain is only 1.10×. Few surviving rows leave little work to amortize the mask over.
  • Q1 gains less than filters1.25× on TPC-H Q1 against 1.94× on the filter pipeline, because arithmetic and hashing dominate once rows survive.
  • One core, one machineSingle-threaded medians on an M2 Pro. No parallel scan, no SIMD intrinsics written by hand: what the compiler auto-vectorizes is what you get.
