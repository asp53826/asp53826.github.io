how it works

The virtual-memory trick, applied to attention.

The cache is one flat tensor per layer, chopped into 16-token blocks. A sequence doesn't own contiguous memory. It owns a block table, and attention gathers through it. That one indirection lets a sequence grow a block at a time instead of reserving its worst case up front.

Continuous batching

The batch is rebuilt on every forward pass. A finished sequence frees its slot immediately and a queued request takes it on the very next pass. Prefill and decode share one token budget, so a long prompt is sliced across passes instead of stalling everyone else.

Prefix caching

Every full block gets a hash of all tokens up to it, chained through the previous block's hash, and is published the moment it fills. With a 256-token system prompt shared by 48 requests, that bought +49% throughput and 1.8× better TTFT.

Invisible from outside

Greedy decoding has exactly one right answer, so the tests assert identical output across block sizes, prefix caching on and off, chunked prefill budgets, batch composition, forced preemption, and speculative decoding at every k.

being straight about what this is

A serving layer, measured honestly.

  • The weights are randomThe text is nonsense on purpose. Random weights do the same arithmetic and move the same bytes, which is what the scheduler and cache are measured on.
  • numpy on CPU, not CUDARatios between configurations hold because every row runs the same code path. Absolute tok/s means nothing outside this machine.
  • Attention loops in PythonProjections, MLP and LM head are batched across the step. The per-sequence attention loop is the part a fused GPU kernel would flatten.
  • Not implementedTensor parallelism, CUDA graphs, quantization, LoRA, swap-to-CPU preemption, beam search.
